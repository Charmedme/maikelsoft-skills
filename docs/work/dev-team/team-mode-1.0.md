# dev-team 1.0.0: the team mode of the dev-flow chain

This note records the decisions of step 7 of plan version 7. In this step, dev-team becomes the team mode of the dev-flow chain. dev-flow 3.1.0 has the hand-over lines. Nobody could answer questions during the work, so each decision takes the recommended answer. A review found gaps, and a fix pass closed them (D20 to D24). The owner can change each one before the release.

## Sources

- Plan version 7: the principles, the commands, "Out of the menu", the hand-over files, and the size table.
- Design version 7.2, section 6 (the hand-over files) and section 7 (the move to the new names).
- dev-flow 3.0.0 as released: `build`, `review-comments`, and the shared scripts `runheader.py`, `specsync.py`, `speclock.py`, `riskcheck.py`, `cycle.md`, and `review-rules.md`.
- Balancing Coupling in Software Design (Vlad Khononov): the two plugins share only a contract (the files and the header). Neither reads the internals of the other.

## Decisions

| No | Decision | Reason |
|----|----------|--------|
| D1 | `plugin.json` of dev-team declares `"dependencies": ["dev-flow"]`, with no version range. The README and the CHANGELOG say "dev-flow 3.1.0 or later". | Design 7.2 says: no version ranges, so the tags stay `<plugin>-v<version>`. A range resolves to tags of the form `<plugin>--v<version>`, which this repository does not make. The marketplace always ships its current dev-flow, which is 3.1.0 or later. |
| D2 | The hand-over happens in step 4 of `build`, after the spec copy. The team takes over `run.md`, `ticket.txt`, `spec.md`, `spec-baseline.json`, and the locks. It changes only `flow` to `team` in the header. | The spec, its fingerprints, and the size exist at that point. The team does not read the ticket again or copy the spec again, so the baseline stays the same. |
| D3 | In `build`, the route step `team` of the role line decides. `ask` offers the team, `on` takes it without the question, and `off` does not offer it. | The plan: "the tech lead route takes the team without the question". `rolestore.py` of dev-setup gives a tech lead `team=on`, and the other roles `team=ask`. |
| D4 | `story-intake` writes `spec.md`: the spec block from `specsync.py copy`, then a section "## Item" with the acceptance criteria verbatim, the mock-up lines, and the notes. After a hand-over, it adds only the section "## Item". | The plan: `story.md` becomes `spec.md`. The team still needs the criteria and the mock-up lines that `story.md` held. One file keeps one place for the item. |
| D5 | An item without a Behaviour spec, or with a draft spec, stops the team. The refine pass of `build` comes first. A chore or a task needs no spec. | The refine pass lives in dev-flow. A copy in dev-team is a second source of the same rules. The team is the mode of `build`, so `/build <item>` is the entry. |
| D6 | G1 is the plan gate. It shows the section "## Checks" of `spec.md` as the list of scenarios. The approval covers the lock of each rule that is not high risk. | dev-flow: the approval of the list of scenarios at the plan gate covers the lock. |
| D7 | The senior writes the test file of each rule first in `build-core`, also for the rules of a package. It runs each red, then locks it with `speclock.py`. A high-risk rule stops with `NEEDS_HUMAN` and "Locks to approve", and the lead asks the human once for all of them. | dev-flow asks the human for each high-risk test file before its lock. An agent cannot ask the human, and the `NEEDS_HUMAN` loop of the team exists. One stop for all high-risk rules keeps the run short. Acceptance tests before the code is the outer loop of the scenario build. |
| D8 | Both flows use one lock file (`.dev-flow/spec-lock.json`) and the guard hook of dev-flow. | dev-flow is a dependency, so its hook is active in a team run. One lock file means that a team run and a solo run see the same locks. |
| D9 | Held-back tests: a new general-purpose agent writes them after G1, from `spec.md` and the part "Acceptance tests" of `design.md`. The lead runs them in a new step "Prove" before G2. A failed test gets one fix pass (counter `heldback-fix`). | The size table of the plan says "Held-back tests: yes" for the team. In a light run there is no reflector, so a separate agent writes the tests in each run. |
| D10 | `heldback.py` moves to `shared/heldback.py`, and `sync_shared.py` copies it to each skill that names it. The script did not change. | The sync keeps one source for each shared file, so no copy goes out of date. The copy in `build` stays the same file, so dev-flow has no change of content. |
| D11 | No mutation check in the team. | The size table of the plan has no mutation row for the team. The reviews and the held-back tests stay. A later version can add it. |
| D12 | The branch follows the branch rules of the project, else `feat/<item>` or `fix/<item>`. A run from 0.6.0 keeps `dev-team/<slug>`. The work folder is `docs/work/<item>/` with the ticket key. | Design 7.2: "one branch rule". The work folder is the folder of the chain. |
| D13 | `runcheck.py` reads the shared header (`RUN-HEADER`) and the section "## Checks" (`RUN-SPEC`) itself. It does not import `runheader.py`. A test checks that the fields and values are the same in both scripts. | Each skill gets its own copy of each script, and the tests import the scripts from their source folders. A second import path is a new way to fail. The test keeps the two lists equal. |
| D14 | `runcheck.py` accepts `story.md` only in a run with `baseline: legacy`. The G2 table with the columns "Rule (verbatim)" and "Locked test" replaces the table "Criterion (verbatim)", and the old table still passes for an old run. | Work in progress carries over (plan). `runheader.py adopt` already gives an old team run `flow: team` and `baseline: legacy`. |
| D15 | `process-review` stays the team mode of `review-comments`. It reads the header, uses `review-rules.md` and `cycle.md` from `shared/`, and stops at the round cap of the size. It keeps its draft replies: the human pushes and posts. | The classes were already the same. The round cap by size was missing. The rule "do not push, do not post" works in 0.6.0, and a rule that works stays. |
| D16 | `review-comments` gives a team run to `process-review` only when dev-team is installed. Without dev-team, it handles the comments itself. | Design 7.2: "For `flow: team` with dev-team installed". A colleague without dev-team can still handle the comments. |
| D17 | All 7 skills of dev-team get `user-invocable: false`. The README section "Commands" names the dev-flow commands and the agents. The description of `deliver-story` keeps the trigger "let the team do it". | The plan: out of the menu, but other skills still start them. The model can still start a hidden skill. |
| D18 | The session-start hook leaves the route to dev-setup only when it is sure that dev-setup prints a role line. dev-setup must be in `plugins/installed_plugins.json` with the scope `user` or a `projectPath` of this folder. `enabledPlugins` must enable it (project settings first, then user settings). A role must be set: `DELIVERY_ROLE`, or a global entry in `roles.json` of dev-setup. In each other case, the hook gives the route. The rules always go to the session. | A hook cannot ask Claude Code which plugins are on, and dev-setup prints nothing without a role. When the hook gives the route next to dev-setup, the only cost is a line twice. A missing route costs more. |
| D19 | dev-flow 3.1.0 is released with dev-team 1.0.0. Each text says "dev-flow 3.1.0 or later". | dev-team 1.0.0 needs the hand-over lines of dev-flow. These are the route step `team`, the start of a `flow: team` run, and the fallback of `review-comments`. dev-flow 3.0.0 does not have them. |
| D20 | On a hand-over, `spec.md` already has the section "## Checks" from step 3 of `build`. The senior updates that table, and adds it only when it is missing. | One table for each work folder. A second table hides the first one from the checkers. |
| D21 | A run with `baseline: legacy` skips the held-back tests (step 6) and the prove step (step 11). G2 says so in Warnings. | A run from 0.6.0 has no rules in `spec.md`, so it has no locks and no held-back tests. `heldback.py run` would stop with exit code 2. |
| D22 | A `run.md` without a header gets `runheader.py adopt` first, in `build` and in `review-comments`. Then the skill reads the header again. | A team run from 0.6.0 has no header, so `runheader.py read` stops with exit code 1 before the `flow: team` check. |
| D23 | A hand-over writes `--flow team --baseline set` when `spec-baseline.json` exists, and replaces the solo body of `run.md` with the team body. The PO decisions of the solo body stay in a section "## PO decisions". | The header shows the state of the baseline, and `run.md` keeps one `#` heading. |
| D24 | The team gets a docs step before G2 (step 12), with `docscheck.py` from `shared/` and one fix pass of the senior (counter `docs-fix`). G2 becomes step 13. | A solo build has this step (step 9 of `build`). The team mode does the same steps. |

## Open points

- The delivery suite has no run of 1.0.0. The eval prompts of the arm `team` give a `story.md` without a Behaviour spec, so the new `story-intake` stops on them. Plan step 9 changes these prompts to the tickets with a spec.
- The detection of dev-setup in the hook ran on Linux only.
- The ux-designer agent reads `story.md` of the work folder. The team says in the prompt that the item is in `spec.md`. A change of the agent is a ux-design change.
