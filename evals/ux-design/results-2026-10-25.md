# Test results: ux-design 0.2.0

Date: 2026-10-25. The tests compare the baseline, the previous version, and the new version. The harness is `run2.py`, `score2.py`, and `grade2.py` with `evals2.json`. Total cost: about $160.

## Summary

| Part | Result | Verdict |
|------|--------|---------|
| A. Prototype (agent) | v1 lost to the baseline on the question and test readiness (0-6). v2 wins 5 of 5 criteria against the baseline. It also wins each criterion against v1. | Use v2 |
| A. Prototype (`product-prototype` on the shell) | v2 (shell and risk ranking) beats the old version on the question (4-0), states (5-1), and test readiness (6-0). The old version wins clarity (5-0): see finding 5. | Use |
| B. Review | The plugin does not find more defects than a capable model with a good prompt. It gives a verdict, severities, screenshots for each state, and a walk file that stays in the repository. | Use for the gate, on Sonnet |
| C. Handoff | The new rules cover 100% of the design states with examples (6 of 6 runs). The old rules cover 53% to 76%. About 10% more cost. | Use |
| Triggers | `ux-prototype` 5 of 5 starts, 5 of 5 quiet. `ux-review` 5 of 5, 5 of 5. | Pass |

Findings:

1. v1 took a research gap ("slot first or technician first?") as its question. The baseline took the risk that the design names itself. Its question: does the planner see before the click which work orders stay unplanned?

   v2 ranks the candidate questions by risk. All 3 v2 runs took the risk question.
2. The test plans of the baseline had hypotheses with a pass rule and a decision for each result. They also had a moderator script, a session plan, and a pilot. v2 has a template with these parts. Test readiness is the closest win (3-2).
3. v1 left out the failure states. v2 adds the failure states of the path. It shows 13 to 16 states, against 7 to 8.
4. The screenshots of the baseline show mostly the setup screen of its own moderator panel. The graders then judged its states from the test plan. This limits the states and clarity grades.

v2 adds the risk ranking of the question to `product-prototype`. Opus, 3 runs. Cost for each run: $3.35.

| Criterion | Old vs v2 | v1 on the shell vs v2 | Baseline vs v2 |
|-----------|-----------|-----------------------|----------------|
| Question | v2 4-0 | v2 4-0 | baseline 5-0 |
| States | v2 5-1 | v2 4-2 | v2 3-2 |

5. The clarity loss comes mostly from the screenshots. The scorer shoots the Explore view of the shell, with the toolbar and the notes panel. There the frame shrinks to about 68%. A participant in Test mode does not see the toolbar, but the product owner sees it in Explore. This is a cost of the shell standard.
6. `product-prototype` is a tool for the product owner ("Is this what you mean?"), not for a test with users. Thus the baseline, which wrote a full user test, wins test readiness against it. The agent in prototype mode is the tool for a test with users.

## B. Review

A built app of FL-31 (vanilla JS, Python server, 19 states) from the approved design. Three copies: clean, 6 easy defects, and 6 subtle defects. A Sonnet reader maps the findings of `ux-review.md` to the defects.

| Variant | Easy defects (of 18) | Subtle defects (of 18) | Subtle, without D5 (of 15) | False findings (subtle) | Verdict and severity | Cost for each run |
|---------|----------------------|------------------------|----------------------------|-------------------------|----------------------|-------------------|
| Opus baseline, long prompt | 18 | 18 | 15 | 0 | yes | $1.96 |
| Opus agent v1 | 18 | 18 | 15 | 0 | yes | $2.21 |
| Sonnet baseline, long prompt | 18 | 17 | 15 | 5 | yes | $0.93 |
| Sonnet agent v1 | 18 | 14 | 14 | 3 | yes | $0.84 |
| Sonnet agent v2 | 18 | 16 | 15 | 1 | yes | $0.80 |
| Sonnet baseline, short prompt | not run | 16 | 15 | 8 | no verdict, no severity | $0.37 |
| Sonnet agent v2, short prompt | not run | 14 | 14 | 2 | yes | $0.69 |
| Sonnet agent v3, short prompt | not run | 15 | 15 | 6 | yes | $0.88 |

The long prompt of the baseline already holds most of the method: 3 widths, fake server answers, axe-core, and the fields of a finding. The short prompt is "review the built feature against the approved design".

Findings:

1. The plugin does not find more defects. Each variant finds the easy defects. On the subtle set, all variants find 14 to 15 of the 15 clear defects.
2. D5 (the empty state for filters has no own "Clear filters" button) is not clear. The design names "Clear filters" as the recovery, and the filter bar still has that button. The plugin variants report "matches" for this state. Two fixes in the walk rules did not change that, and they are correct for the design as written.
3. What the plugin adds: each run gives a verdict and a severity for each finding. It makes 48 to 84 screenshots of the states at 3 widths. Its walk file in `tests/ux/` runs again after the fix. The short-prompt baseline reads the code, makes 0 to 5 screenshots, and gives no verdict. Thus a gate cannot use its result.
4. On Sonnet the agent costs $0.70 to $0.90 for each run. It finds the same as Opus without the plugin, at about 45% of the cost.
5. On the clean app, all variants found the same 2 real P1 faults that the sub-agent built in by accident. These are not false findings. The undo of the toast is not reachable by keyboard in 8 seconds. The panel accepts a date in the past.
6. This test found a fault in the tool. `uxcheck.py` counted a hidden date input (opacity 0) as an input without a label. The visibility rule now skips invisible elements.

## D. Calls

Not tested at runtime. A headless run cannot install the plugin and call the agent with the Agent tool in the same harness. The unit tests check the new rule of `runcheck.py` (a run with `ux-design.md` needs the UX review before G2). The calls are text in the skills, the same pattern as the existing `example-mapping` call.

## Versions

- `ux-prototype` v2: risk ranking of the question, a test-plan template, and the failure states of the path.
- `ux-review` v3: each state ends with `expect_text` checks inside the element of the state, and the empty-state rule.
- `uxcheck.py`: review mode, and invisible elements are skipped.
