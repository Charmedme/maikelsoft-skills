## Configuration classes and conventions

Put each entity configuration in an `IEntityTypeConfiguration<T>` class. Load all of them with `ApplyConfigurationsFromAssembly`. Put defaults for a type in `ConfigureConventions`:

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder builder)
{
    builder.Properties<decimal>().HavePrecision(18, 4);
    builder.Properties<string>().HaveMaxLength(256);
    builder.Properties<OrderStatus>().HaveConversion<string>().HaveMaxLength(20);
}
```

- Decimal (DATA-11): without precision, SQL Server uses `decimal(18,2)` and cuts the extra digits with no error. EF logs `SqlServerEventId.DecimalTypeDefaultWarning`. PostgreSQL uses `numeric` without precision.
- String: SQL Server uses `nvarchar(max)` without a length, and `nvarchar(max)` cannot be an index key. On PostgreSQL, `text` and `varchar(n)` perform the same, so a length is a business rule there.
- Enum (DATA-12): a string survives a new order of the members, and it is readable in SQL. Add `IsUnicode(false)` on SQL Server.
- A property configuration overrides the convention: `money.Property(m => m.Amount).HasPrecision(19, 4)`.

## Complex types (value objects and JSON)

EF 10 maps value objects as complex types. A complex type has no key and no identity. Two objects with the same values are equal.

```csharp
// Columns in the Orders table: Total_Amount, Total_Currency.
builder.ComplexProperty(o => o.Total, money =>
{
    money.Property(m => m.Amount).HasPrecision(19, 4);
    money.Property(m => m.Currency).HasMaxLength(3).IsFixedLength();
});
builder.ComplexProperty(o => o.ShippingAddress);

// One JSON column: json on SQL Server 2025, jsonb on PostgreSQL.
builder.ComplexProperty(o => o.Details, details => details.ToJson());

// A list of value objects in one JSON column.
b.ComplexCollection(s => s.Parcels, parcel => parcel.ToJson());
```

- A complex collection must use `ToJson()`. EF does not support collections of structs.
- `ExecuteUpdate` can set JSON properties only on complex types.
- A record type works well as a value object: replace the whole object to change it.
- Owned types (`OwnsOne`, `OwnsMany`) are entity types with a hidden key. Keep them in existing code. EF 11 marks owned JSON collections without a key as obsolete.
- Do not use `[Column(TypeName = "jsonb")]` on a POCO for PostgreSQL. That is the old EFCore.PG mapping.

## Value converters and strongly typed IDs

A value converter maps a .NET type to a column type. Register it one time per type in `ConfigureConventions`. Use strongly typed IDs only when DATA-08 says so:

```csharp
public readonly record struct ShipmentId(Guid Value);

public sealed class ShipmentIdConverter() : ValueConverter<ShipmentId, Guid>(id => id.Value, value => new ShipmentId(value));

// In ConfigureConventions:
builder.Properties<ShipmentId>().HaveConversion<ShipmentIdConverter>();

// In OnModelCreating, so that EF generates the key:
b.Property(s => s.Id).ValueGeneratedOnAdd();
```

- Use a `struct`, so equality works without a value comparer.
- A converted value cannot use database functions of the target type in LINQ, unless EF can translate the conversion.

## Keys

DATA-07 default: a `Guid` key that the provider generates on `Add`.

| Provider | Generator | Result |
|----------|-----------|--------|
| SQL Server | `SequentialGuidValueGenerator` (default) | Ordered for the SQL Server `uniqueidentifier` sort order |
| PostgreSQL (EFCore.PG 9+) | `NpgsqlSequentialGuidValueGenerator` (default) | UUIDv7 |

- Do not set `Id = Guid.NewGuid()`. A random key fragments the clustered index on SQL Server and the B-tree on PostgreSQL.
- Do not use `Guid.CreateVersion7()` for a SQL Server clustered key. SQL Server sorts the bytes of a `uniqueidentifier` in another order, so v7 values are not in order there.
- The EF provider (EFCore.PG) generates the UUIDv7 value, not the Npgsql ADO.NET driver. Dapper inserts do not get it.
- `int` and `bigint` keys use `IDENTITY` on SQL Server and `GENERATED BY DEFAULT AS IDENTITY` on PostgreSQL (not `serial`). Use HiLo or a sequence only with a reason.

## Time types

DATA-10 default:

| Value | .NET type | SQL Server | PostgreSQL |
|-------|-----------|------------|------------|
| Instant (an event happened) | `DateTimeOffset`, UTC | `datetimeoffset` | `timestamptz` (offset must be zero) |
| Calendar date | `DateOnly` | `date` | `date` |
| Time of day | `TimeOnly` | `time` | `time` |
| Duration | `TimeSpan` | `time` (under 24 hours) or `bigint` ticks | `interval` |
| Time zone of a user | `string` (IANA ID) | `varchar(64)` | `text` |

- Read "now" from `TimeProvider` (`clock.GetUtcNow()`). Tests then use `FakeTimeProvider`.
- Do not write `DateTime.Now`. On PostgreSQL, Npgsql throws when a non-UTC value goes to `timestamptz`. Do not set `Npgsql.EnableLegacyTimestampBehavior` to hide it.
- Npgsql 10 reads `date` as `DateOnly` and `time` as `TimeOnly` by default.
- NodaTime is the option for real calendar rules (DATA-10). It needs the provider plugin (`UseNodaTime()`).

## Interceptors and audit columns

DATA-14 default: one `SaveChangesInterceptor` fills `CreatedAt` and `UpdatedAt`.

```csharp
public sealed class AuditInterceptor(TimeProvider clock) : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData,
        InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {
        if (eventData.Context is { } context)
        {
            var now = clock.GetUtcNow();
            foreach (var entry in context.ChangeTracker.Entries<IAudited>())
            {
                if (entry.State == EntityState.Added)
                {
                    entry.Entity.CreatedAt = now;
                }

                if (entry.State is EntityState.Added or EntityState.Modified)
                {
                    entry.Entity.UpdatedAt = now;
                }
            }
        }

        return base.SavingChangesAsync(eventData, result, cancellationToken);
    }
}
```

Register it as a singleton and add the same instance to each context:

```csharp
services.AddSingleton(TimeProvider.System);
services.AddSingleton<AuditInterceptor>();
services.AddDbContext<AppDbContext>((sp, options) => options
    .UseSqlServer(connectionString)
    .AddInterceptors(sp.GetRequiredService<AuditInterceptor>()));
```

- A new interceptor instance for each context makes EF build a new internal service provider each time.
- Register an interceptor with state per request (the current user) as scoped. Then resolve it in the `AddDbContext` lambda, and do not use pooling.
- `ExecuteUpdate` and `ExecuteDelete` do not call `SaveChanges` interceptors. Set the audit columns in the setters.
- A `DbCommandInterceptor` sees each SQL command, also from `ExecuteUpdate`. Use it for command tags or diagnostics, not for business rules.

## Query filters: soft delete and multi-tenancy

EF 10 named filters let a query switch off one filter and keep the others:

```csharp
modelBuilder.Entity<Order>()
    .HasQueryFilter(Filters.SoftDelete, o => !o.IsDeleted)
    .HasQueryFilter(Filters.Tenant, o => o.TenantId == TenantId);

// Admin view: deleted rows too, the tenant filter stays on.
db.Orders.IgnoreQueryFilters([Filters.SoftDelete])
```

- Soft delete (DATA-13): the default is a hard delete. When the human picks soft delete, also add filtered unique indexes, so that a deleted row does not block a new row. Add an interceptor that turns `Remove` into an update, and a plan for a GDPR erasure. `ExecuteDelete` deletes rows for real.
- Multi-tenancy (DATA-16): the filter reads a property of the context (`TenantId => tenant.TenantId`). EF reads it for each query. Do not use `AddDbContextPool` with this field, because a pooled context keeps the field of the last request.
- Start each index of a tenant table with the tenant column.
- `IgnoreQueryFilters()` without names switches off all filters, also the tenant filter. Name the filters.
- Raw SQL through `FromSql` also gets the filters, because EF wraps the SQL in a subquery.

## Seed data

DATA-19 default:

- Reference data that is the same in each environment: `HasData`. It becomes part of the migrations. Give each row a fixed key.

  ```csharp
  modelBuilder.Entity<Country>().HasData(
      new Country { Id = 1, IsoCode = "NL", Name = "Netherlands" },
      new Country { Id = 2, IsoCode = "DE", Name = "Germany" });
  ```

- Environment data (an admin user, demo data): `UseSeeding` and `UseAsyncSeeding`. They run after `Migrate`, `dotnet ef database update`, and a bundle. They do not run for SQL scripts. Write both, because the tools call the sync version. Make them idempotent.

  ```csharp
  .UseSeeding((context, _) =>
  {
      var customers = context.Set<Customer>();
      if (!customers.IgnoreQueryFilters().Any(c => c.Email == "demo@example.com"))
      {
          customers.Add(new Customer { Name = "Demo", Email = "demo@example.com" });
          context.SaveChanges();
      }
  })
  .UseAsyncSeeding(async (context, _, ct) =>
  {
      var customers = context.Set<Customer>();
      if (!await customers.IgnoreQueryFilters().AnyAsync(c => c.Email == "demo@example.com", ct))
      {
          customers.Add(new Customer { Name = "Demo", Email = "demo@example.com" });
          await context.SaveChangesAsync(ct);
      }
  })
  ```

- Test data: inside the tests only.

## Several contexts in one database

In a modular monolith (DATA-03, DATA-04), each module context has its own schema and its own migrations history table:

```csharp
modelBuilder.HasDefaultSchema("shipping");

options.UseSqlServer(connectionString, o => o
    .MigrationsHistoryTable("__EFMigrationsHistory", "shipping"));
```

A transaction across two contexts is a sign that the module boundary is wrong. Use an outbox and a message (MSG-09).
